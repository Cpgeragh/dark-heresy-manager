# Build environment validation

Hosting's existing predeploy hook rebuilds the app, checks the PWA inventory, and
then runs `scripts/checkBuildEnvironment.mjs`. Unknown or missing deployment
targets stop the hook before building. Only the production and staging project
IDs listed in `scripts/deploymentTargets.json` are allowed.

The Vite build records a SHA-256 fingerprint of its resolved Firebase API key,
auth domain, project ID, storage bucket, sender ID, app ID and App Check site key.
This includes environment-variable overrides. It also records the build mode and
hashes of the compiled JavaScript files. Firebase settings supplied through Vite
`define` overrides are rejected so they cannot disagree with the recorded resolved
environment. Local performance builds do not create a deployable build record.

After building, the checker compares the fingerprint and mode against the
independently saved target, checks the compiled file hashes, and confirms that
`index.html` loads a verified entry point. Missing records, wrong environments and
mixed output stop the deployment before upload. The checker prints the project
and mode only, not the API key or other connection values.

The initial saved fingerprints come from the existing production `.env` and the
merged `.env`/`.env.staging` settings. These are trusted configuration baselines,
not an online verification of project ownership. They are never regenerated by
the deployment hook. If intended Firebase settings change, review the change and
update the corresponding fingerprint deliberately. Do not overwrite a saved
fingerprint merely to make a failing deployment pass.

For an existing build, run `node scripts/checkBuildEnvironment.mjs PROJECT_ID`.
The check does not upload or modify server data. Deployment remains a user action.
